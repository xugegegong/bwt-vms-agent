# BWT-VMS 交付智能体套件

这是一个**工具无关**的交付智能体套件：任何 AI 编码 / 代理工具都能加载它，拿到同一套知识、技能和船舶台账。目标是让不同交付人员用各自习惯的工具，开一个新会话就能直接进入交付状态。

## 目录结构

| 目录 / 文件 | 作用 |
|---|---|
| `AGENTS.md` | 通用系统提示词（人设 + 红线 + 工作流），任何工具先把它作为系统指令加载 |
| `knowledge/` | 知识库：架构、功能设计 D01–D16、交付操作手册、数据字典、环境与数据库 |
| `knowledge/待确认/` | **待审区**：交付中发现的新经验 / 纠错提案，组长确认后才移入权威区 |
| `skills/` | 交付技能 markdown（S0–S6 + FAQ + SVG 规则），工具无关 |
| `ships/` | 每船台账（进度、配置留痕、踩坑），一条船一个文件 |
| `memory/` | 团队级记忆：当前上下文 current-context、决策 decisions/、运行日志 run-log |
| `tools/` | S1 采集工具脚本（make_jsonstring / apply_to_iscu / iscu_agent_api 等） |

## 四种工具的接入方式

**通用原则**：把本仓库设为工作目录，把 AGENTS.md 内容作为系统提示 / 指令加载。

- **Claude 桌面**：挂载本仓库为工作文件夹；会话开始让它"先读 AGENTS.md 和本船台账"。已装好的 skill（bwt-vms-*）可直接触发。
- **Codex**：仓库根目录的 AGENTS.md 会被自动读取；直接让它按 AGENTS.md 的规则工作。
- **workBuddy / zcode**：把本仓库设为工作目录 / 知识库，首条消息粘贴 AGENTS.md 全文，或明确"始终遵循 AGENTS.md"。

## 一次典型交付会话怎么开

1. 加载 AGENTS.md（或让它先读 AGENTS.md）。
2. 说："我要配 XX 船，先读 ships/XX.md 和 skills/ 里的 S0。"
3. 按技能步骤推进，每步让它更新台账。
4. 排错时说："XX 船出现 XX 症状" → 让它查 skills/bwt-vms-faq.md。

## 台账规则

- 一条船一个文件 `ships/<船号>.md`，用 `ships/_模板.md` 新建。
- 每次会话收工前，把本次改动（表 / 字段 / SQL 摘要 / 环境）写回台账。

## ⚠️ 连接纪律（人人必须遵守）

**开发 / 测试环境都是公司共享资源，不是可以随便连的。**

1. **连之前先说、并取得明确指令** —— 讲清"连哪个环境、哪个库、做什么"，同意后才连
2. **不得随意连接** 别人负责的环境；**更不得随意修改、删除**其中的数据库 / 配置 / 服务
3. **已获准连接后，凡遇修改或删除**：先说明影响面 → **先备份** → **再问一次** → 得到明确答复才执行
4. **换环境 / 换库 / 扩大范围** 都要重新确认
5. 文档里出现的内网地址（`192.168.x.x`）**只是说明"环境长什么样"**，不代表可以直接连；
   旧环境可能已停用，连前先跟环境负责人核对

> 完整红线见 `AGENTS.md`；环境说明见 `knowledge/环境与数据库.md`。

## 使用规范（人看版；智能体版见 AGENTS.md）

### 开工四步

1. **读 `memory/current-context.md`** —— 先知道整体到哪一步、有什么已知坑
2. **同步知识库** —— `git pull`，确认是最新（⚠️ 若尚未建仓库，见下方「前置」）
3. **告诉智能体当前环境** —— 现场 / 办公室 / 酒店VPN，及连接信息（它每次都会问，不写死）
4. **读本船台账** `ships/<船号>.md` —— 没有就用 `_模板.md` 新建

### 收工四步（★ 别跳，跳了这次白干）

1. **写本船台账** —— 改了什么表/字段、为什么、在哪个环境
2. **有全局变化就更新 `memory/current-context.md`** —— 下一个人靠它接手
3. **可复用的经验提一条到 `knowledge/待确认/`** —— 附证据（SQL/日志/实测结果）
4. **`git commit && git push`** —— 不提交，别人拿不到

> 台账模板末尾有「收工自检」清单，照着过一遍即可。

### ⚠️ 前置：先把套件纳入 git 仓库

**当前 `bwt-inland-feature/` 目录没有 `.git`**（看着像从 GitLab 下载的 zip）。
没有版本控制，"共享知识 / 别人拉到最新 / 变更留痕 / 回滚"**全都做不到**——也就退化成了每人本地各一份，正是要避免的碎片化。

**建议**：把 `bwt-vms-agent/` 单独建一个 git 仓库（或纳入公司 GitLab 的某个项目），全员 clone 同一份。
**在此之前**，第 2、4 步只能靠人工传文件，请务必提醒交付人员"确认拿到的是最新副本"。

## 知识维护规矩（重要，人人要守）

### 单一真源

`bwt-vms-agent/` 是唯一真源。不要在自己电脑上另存一份改，改了别人就看不到。

### 技能有两份副本，改一处必须同步另一处

- **Claude 已装技能**：真正被 Claude 触发加载的那份（用 `save_skill` 更新）
- **套件副本**：`skills/*.md`（codex / workBuddy / zcode 读这份）

改技能时：**先对比两份、以内容更全的为底做合并，再两边各写一遍**。绝不无条件覆盖——有过教训：套件副本曾比已装版少 8 条实战经验，直接覆盖就会丢掉。

### 知识分三层，别把推测当权威

| 层级 | 标记 | 什么算 |
|---|---|---|
| 权威 | `已确认` | 组长 C 确认过，或代码/数据库实测验证过 |
| 实战 | `实战验证` | 交付人员现场验证有效，未经 C 确认 |
| 推测 | `AI 生成待验证` | AI 整理推断，没人验证过 |

**现状**：`knowledge/` 里大部分文档是 AI 生成的，默认都算第三层，直到有人逐条确认。智能体读到第三层内容时会主动声明"未经验证"。

### 经验怎么回流（每个人的活）

1. 交付中用智能体时，把新发现写进 `knowledge/待确认/`（复制 `_模板.md`），标明提出人/日期/环境/**证据**
2. 智能体之后读到它，会自动标明"这条尚未经确认"
3. 组长 C 审核：确认的移入 `knowledge/` 标 `已确认`；否掉的记下原因后归档
4. 提交 git，其他人下次会话拉到即生效

**证据是硬门槛**：光说"我觉得"不行，要附 SQL、日志、实测结果。这样审核的人不用重新查一遍。

### 开工先同步

每次会话第一步先拉取最新知识（git pull），并确认知识库版本——避免用旧知识操作。智能体开工时也应报告当前版本。

### 当权威也出错时

组长 C 的业务口径优先于 AI 生成内容和一般经验。但**如果 C 的说法与代码/数据库实测矛盾，智能体应当把冲突摆出来**（"C 说 X，但实测是 Y，证据如下"），由 C 定夺——不盲从权威，也不盲从 AI。
