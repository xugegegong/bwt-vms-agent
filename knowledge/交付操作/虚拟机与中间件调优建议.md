# 虚拟机与中间件调优建议（CentOS 8 · 8C/16G/1T · iCommander 整栈）

> 知识层级:**AI 生成待验证**——基于 2026-11-11 对 192.168.7.127 拷贝环境的实测配置逐条对照得出,每条都注明实测依据;落地前先在测试环境验证,再由 C/交付负责人确认。
> 实测现状:deploy-standalone.sh 里**没有任何 sysctl/ulimit/内核调优**;组件配置=各官方默认+少量手工改动。
> 实施方式:建议在 deploy-standalone.sh 里新增 `optimize_sys()` 环节(文末有可粘贴代码),把调优固化进部署,别再手工改。

## 一、实测现状盘点（哪些已 OK，哪些是坑）

| 项 | 实测值 | 评价 |
|---|---|---|
| vm.swappiness | **60（默认）** | 🔴 坑：Kafka/MySQL 最怕换页,127 环境的 CPU 占满事故就是 swap 风暴放大 |
| MySQL innodb_buffer_pool_size | **未配置=默认 128M** | 🔴 坑：库里 tab_data_org 115 万行×8KB PNG(约 9G),128M 缓冲池等于全靠磁盘 |
| MySQL innodb_log_file_size | 未配置=默认 48M | 🟡 写入频繁换 checkpoint,崩溃恢复慢 |
| MySQL max_connections | **4000** | 🟡 反向坑:连接风暴时每连接线程内存可到几百 K,4000 个能把 16G 吃穿 |
| MySQL max_allowed_packet | 默认 4M | 🟡 船岸同步走 SQL 批量,建议放大 |
| Redis maxmemory | **未配置=无上限** | 🔴 坑：内存无界增长直到 cgroup OOM;且无淘汰策略 |
| Redis appendonly | yes + everysec | ✅ 已配好(掉电最多丢 1 秒) |
| Redis FLUSHALL/FLUSHDB | 未 rename | 🟡 历史上"清库"是人工习惯操作,防手滑 |
| Kafka KAFKA_HEAP_OPTS | -Xmx1G -Xms1G | 🟡 16G 机器可给 2G(数据量上来后) |
| Kafka num.recovery.threads.per.data.dir | **1(默认)** | 🟡 每次 kafka 重启加载日志段 68 秒的元凶(现场实测) |
| Kafka num.network/io.threads | 3/8(默认) | 🟡 8 核机器可微调,优先级低 |
| Kafka log.flush.interval.ms | 1000 | ✅ 单 broker 无副本,保留(牺牲吞吐换掉电安全,合理) |
| Nacos JVM | **-Xms512m -Xmx512m** | ✅ 已手工调过(startup.sh 自定义分支),不用动 |
| Docker daemon.json | **空(不存在)** | 🟡 无 live-restore:升级/重启 dockerd 会带停所有容器;无默认日志限制(靠 compose 里逐个配了 10M×3) |
| 容器 ulimit nofile | 默认(低) | 🟡 Kafka/MySQL 长连接多,需要提 |
| somaxconn / file-max / max_map_count | 4096 / 极大 / 极大 | ✅ 已够 |
| THP | madvise | 🟡 够用;追求 Kafka 低延迟可设 never(优先级低) |
| chronyd | active | ✅ 在跑(注意校验时钟源是否真实有效) |
| MySQL 时区 | '+0:00'(UTC) | ✅ 与全链路 UTC 一致,别改 |

## 二、P0 防事故（优先做，都是稳定性直接相关）

1. **vm.swappiness 60 → 1**。实测依据：127 环境 swap 风暴把 load 打到 106。Kafka 的页缓存、MySQL 的缓冲池被换出后性能断崖。改法:`sysctl -w vm.swappiness=1` + 写入 /etc/sysctl.d/。
2. **MySQL 补齐 InnoDB 三件套**:`innodb_buffer_pool_size=3G`(容器限额内)、`innodb_log_file_size=1G`、`innodb_flush_method=O_DIRECT`(绕过双缓冲);同时 `max_connections 4000 → 600`(各服务 druid 池 max 10×8 个服务+python+nacos,600 已 3 倍富余)。
3. **Redis 上限与防误删**:`maxmemory 2gb` + `maxmemory-policy volatile-lru`(全系统 key 基本都带 TTL,安全)+ `rename-command FLUSHALL ""` / `FLUSHDB ""`。
4. **JVM 堆与容器限额对齐**(红线条目):每个 start.sh 的 `-Xmx` ≤ 容器限额一半。实测依据:system -Xmx4G > 限额 2.5G 直接引爆 127 环境。16G 机器建议:system 1280M、dataflow/realTimeData/thirdpartycall 各 768M、health/shiptoshore/websocket 各 512M、gateway 384M、job 256M。
5. **MySQL slow log**:`slow_query_log=ON`、`long_query_time=2`——出问题时这是唯一的取证手段(该项目 Redis 工具类吞异常、服务日志分级混乱,没有慢查询日志等于盲飞)。

## 三、P1 性能与恢复速度

1. **Kafka 恢复线程** `num.recovery.threads.per.data.dir=4`:重启时日志段并行加载,实测 68 秒可缩到约 20 秒——看门狗/运维每次重启 kafka 都受益。
2. **Kafka 堆** 1G→2G(仅当船数据量上来了;数据量小不用动)。
3. **offsets.retention.minutes 1440→2880**:消费停摆 24h 位点被删的场景(11-11 那条船的真实故障)窗口翻倍;看门狗 v2 已兜底,这是双保险。
4. **Docker daemon.json**:`{"live-restore":true,"default-ulimits":{"nofile":{"Name":"nofile","Hard":65535,"Soft":65535}},"log-driver":"json-file","log-opts":{"max-size":"50M","max-file":"3"}}`——升级/重启 dockerd 不再带停全栈;没在 compose 里配日志限制的容器也有兜底。
5. **MySQL** `max_allowed_packet=64M`、`thread_cache_size=64`、`table_open_cache=2000`。

## 四、P2 长效治理

1. **tab_data_org 清理策略**(增长最猛的表,实测 115 万行/约 9G):30 天前数据归档或删除,挂 cron(backup_db 已有,补一个 purge);否则 1T 盘约 3 年见底,且 buffer pool 命中率持续恶化。
2. **node_exporter + 告警**:prometheus/alertmanager 栈已在跑(实测 11 天),补 node_exporter + 三条规则:磁盘>80%、swap 使用>500M、容器 1 小时内重启>3 次。
3. **logrotate**:/var/log 兜底(应用日志 log4j2 已滚动)。
4. THP madvise→never(可选,Kafka 延迟敏感才做)。

## 五、容量红线（诚实结论）

22 个容器的内存限额总和无论怎么分都 >16G(现在 compose 里加起来约 15G,是靠"限额>实际占用"在跑)。实测同栈在 7.4G 机器上实际用 5.6G,16G 机器给 MySQL 3G 缓冲池后实际约 10~11G,**够用但余量不大**。红线:单船数据量持续增长(tab_data_org、多船共 broker)或加装 video/行为识别类服务时,升 24G;否则优先砍监控栈(约 600M)挪余量。

## 六、deploy-standalone.sh 集成代码（可粘贴）

```bash
optimize_sys(){
    info_log "内核参数调优"
    cat > /etc/sysctl.d/99-vms.conf << EOF
vm.swappiness = 1
net.core.somaxconn = 4096
EOF
    sysctl -p /etc/sysctl.d/99-vms.conf >/dev/null

    info_log "docker daemon 配置(live-restore+日志上限+nofile)"
    cat > /etc/docker/daemon.json << EOF
{"live-restore":true,
 "default-ulimits":{"nofile":{"Name":"nofile","Hard":65535,"Soft":65535}},
 "log-driver":"json-file","log-opts":{"max-size":"50M","max-file":"3"}}
EOF
    systemctl restart docker    # live-restore 生效需要重启 dockerd

    info_log "MySQL 配置追加"
    cat >> /opt/mysql/conf/my.cnf << EOF
innodb_buffer_pool_size = 3G
innodb_log_file_size = 1G
innodb_flush_method = O_DIRECT
max_connections = 600
max_allowed_packet = 64M
thread_cache_size = 64
table_open_cache = 2000
slow_query_log = ON
long_query_time = 2
EOF

    info_log "Redis 配置追加"
    cat >> /opt/redis/redis.conf << EOF
maxmemory 2gb
maxmemory-policy volatile-lru
rename-command FLUSHALL ""
rename-command FLUSHDB ""
EOF

    info_log "Kafka 恢复线程与位点保留"
    sed -i 's/^num.recovery.threads.per.data.dir=.*/num.recovery.threads.per.data.dir=4/' \
        /opt/kafka/kafka_2.12-2.1.1/config/server.properties
    echo "offsets.retention.minutes=2880" >> /opt/kafka/kafka_2.12-2.1.1/config/server.properties
}
```

注意事项:①改完需重启对应容器才生效(mysql 的 `innodb_log_file_size` 变更 5.7 会自动重建 redo);②`max_connections 4000→600` 会覆盖脚本里原有 sed 的值,确认 dis_mysql 分发顺序在 optimize_sys 之后;③`rename-command` 改后要 `docker restart redis`;④建议部署顺序:装完分发(dis_*)→ optimize_sys → start_all,并把 optimize_sys 挂进 install_all 流程;⑤每项改完都幂等可重复(cat >> 会重复追加——粘贴版请先 grep 去重,正式版建议改成"检查存在才追加"或直接改分发模板文件)。

## 七、明确不建议动的（避免过度优化）

- Kafka `log.flush.interval.ms=1000`:单 broker 无副本,这是掉电安全的生命线,别为吞吐删掉。
- Nacos JVM 512m:已是最优,RSS 实测 380M。
- somaxconn/file-max/max_map_count:已达标。
- MySQL 时区 UTC:全链路一致,别动。
- compose 里各容器 `deploy.resources.limits`:结构是对的,只需按第二节第 4 条对齐 JVM 堆。
