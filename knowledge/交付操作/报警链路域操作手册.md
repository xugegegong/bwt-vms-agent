> 场景:报警不响/全船报警反色/SVG 开关量显示红色/报警统计/微信推送/新船报警生效配置。

## 0.【结案】开关量 SVG 显示红色而非配置绿色(工单 45241)

**现象**:state_quantity_cfg 配 1=绿,原始值 1,SVG 显示 RUN 文本但红色。

**根因(代码证据链)**:
1. **SVG 图颜色不读 state_quantity_cfg**——它只管列表/总览视图;SVG 颜色来自**绑定时存进 mimic_config 的快照**,报警元素硬编码"值 0→红 / 值 1→绿"
2. 原始值 1 显示红的唯一路径 = 后端把它**归一化成了 0**:dataCleanV2 对 `device_type='0'` 的点按 `tab_alarm_mapping`(dds 1→consistency 0)归一化后写 Redis → 前端拿到 0.0 → 红
3. **结论:该点的 device_type 被错配成 '0'(报警量)。device_type='2' 的点永远不会被归一化,值 1 必绿。这是配置错误,不是前端 bug**
4. RUN 文本还在 = SVG 文件里设计时写死的静态文本(归一化后查 status['0'] 无配置,不更新文本)

**修复(按序)**:
```sql
UPDATE tab_engine_param SET device_type='2' WHERE ship_id=<sid> AND device_key='<该点>';
-- 确认有状态量行(列表视图用,无则补)
SELECT * FROM tab_engine_state_quantity_cfg WHERE ship_id=<sid> AND device_key='<该点>';
```
**生效**:dataCleanV2 缓存 5 分钟;**realTimeData 的报警映射只在启动加载——必须重启 realTimeData**;前端强刷。
**验证**:Redis `GET list:ship:{id}:other` 该点变 "1.0";`HKEYS engine:alarm:device:{id}` 不含该点;SVG 变绿。
**附带**:该点此前污染了报警统计(统计 job 不过滤 device_type),修正后次日起不再计入。

## 1. 报警判定全链路(谁判/判什么)

```
实时值 → dataCleanV2:device_type='0' 的点 → tab_alarm_mapping 归一化 → Redis other(0=报警)
       → realTimeData EngineAlarmListener → Redis hash engine:alarm:device:{shipId}(报警中的点)
       → WS 推前端(Header 报警数/机舱报警列表/SVG 红)
```

**关键纠偏**:
- **判据只有两个**:`device_type=='0'` + 归一化值==0。**tab_engine_param 的 low/high 阈值列不参与报警判定**(纯展示分档)!
- 归一化语义:consistency **0=报警,1=正常**(DDL 注释为准;代码里有处错注释"为0才是正常"勿信)
- 无 alarm_mapping 行的船走默认 `{1→1, 0→0}`(原始 0=报警)
- 三种类型路径:0 报警量→归一化+判报警;1 数值量→不判;2 状态量→不判(但 tab_res_status 记变化段)

## 2. tab_alarm_mapping(报警极性,每船 2 行)

| 列 | 说明 |
|---|---|
| ship_id / dds_value(原始) / consistency_value(0=报警) / status | 一船 2 行完整极性 |
| 典型 `(1→0),(0→1)` | 该船 DDS 报警时发 1 |
| 报警时发 0 的船 | 可不配(默认 0→0 即报警),但建议显式配齐 |

**⚠️ 极性配反 = 全船报警全反色**(正常显示报警、报警显示正常)。它是全局一套,不能按点配——所以**报警语义反的传感器必须改 device_type 或让船厂改 DDS 输出**。
分工:alarm_mapping 管报警量统一语义;state_quantity_cfg 管状态量显示样式。互不替代。

## 3. 新船报警生效配置清单(除工况点表外)

1. `tab_engine_param.device_type` **逐点配对**(0/1/2)——45241 的教训:错配 0 整条链走报警
2. relationship+menu 必挂(统计按父菜单归组,不挂不进统计)
3. `tab_alarm_mapping` 每船 2 行(按 DDS 极性)
4. `state_quantity_cfg`:每个 type=2 点一行(**键从 0 连续**——列表组件用数组下标取值,跳号取错条目)
5. `tab_app_wx_engine_important_alarm`:需要微信推送的重点点(不配不推)
6. `attention_level` L1-L5(按等级统计用)
7. SVG 图上绑定的颜色/文本是**设计时快照**,改表不回填——组态编辑里改后重新保存

## 4. 报警统计(tab_alarm_statistics,3955 行)

- 写入:每天 00:30 定时 job,从 `tab_res_status`(is_read=0 且值=报警dds)按天补齐,粒度=**船×工况点×天**,记父菜单(饼图分组),处理后置 is_read=1
- 读取:报警统计分析页,4 种维度(按日期/按航次/按严重等级/按频次);导出复用同 service
- ⚠️ 统计 job 不过滤 device_type——状态量值恰等于报警 dds 值会被误计(45241 副作用)

## 5. 推送/声音/反馈

- **前端**:WS 随船位消息推 alarmTotal;机舱页 Header 报警下拉+badge;**网页端报警本身无声音**(只有"信号丢失"且 E 认证开关开时播放 alarm.mp3)
- **真声光报警在船端**:sl-alarm.switch=true 时 SoundOpticalAlarmService 检查报警 hash−忽略清单 → 写声光状态;消音=并入 `sl:alarm:device:ignore:{shipId}`
- **微信推送**:配置 important_alarm 点 → Kafka engine-important-alarm → 与上次记录做差 → 新增 INSERT 消息表推送
- **报警反馈表 tab_alarm_feedback 零代码引用**(遗留空表,当前无报警确认闭环)

## 6. 排错速查

| 症状 | 查 |
|---|---|
| 全船报警反色 | tab_alarm_mapping 极性(2 行对不对) |
| 单点常红不恢复 | device_type 是否错配 '0'(45241);Redis other 该点值 |
| 报警数不对 | `HKEYS engine:alarm:device:{id}` vs 前端 badge;改配置后 realTimeData 重启没 |
| 统计里多出不报警的点 | 该点 device_type 与 alarm_statistics 误计(见 §4) |
| 微信不推 | tab_app_wx_engine_important_alarm 配了没;Kafka topic 活着没 |
| 声光不响 | 船端 sl-alarm.switch;忽略清单是不是把点消音了 |
