# 配置中心数据安全风险清单(交付必读)

> 更新日期:2026-09-04(修改本文档后请同步更新此日期,并到 Dify 知识库重新上传该文件)

> 可视化配置(ConfigurationManagement)大量采用"**整船 DELETE 后重插**"模式,且**多数方法无事务、不校验前端载荷是否完整**。交付人员在页面上操作时,只要某次提交载荷不全/误触,对应表整船数据就可能被清空且不可回滚。**此清单按风险排序,交付操作前先看。**

---

## 结论先行(最可能让你"数据没了"的 4 个操作)

1. **`/shipConfig/upload` 配置导入(JSON 路径)** —— 会对 `add_type=0` 的表执行 **`DELETE FROM tab_xxx`(无 WHERE,跨船清空!)** 再用文件重建。文件若只含一条船(最常见的拷贝/导出),会清掉所有其他船的该表数据。
2. **能效设备保存(EnergyEffciencyDevice 页)** —— 载荷里没出现的设备会被逐个 delete;前端空数据/漏传时,整船能效设备+工况点全清。
3. **机舱菜单保存(EngineParamMenu 页)** —— 先删该船该 menuType 整棵菜单树再按前端载荷重建;某子树没展开/漏序列化 → 整棵菜单+工况点绑定丢失。无事务。
4. **特殊信号/通导/流量计保存** —— 按 category/类型/整船删后重插,载荷不全即清空该类全部配置。

---

## 逐项风险明细(按级)

### 【极高】ShipConfigUploadServiceImpl —— 配置导入整表删
- 类:`ShipConfigUploadServiceImpl.uploadExcel / uploadJson / getAllDeleteSql`
- 代码:`if (addType==0){ ... getAllDeleteSql(tableName) → "DELETE FROM "+tableName }`(无 WHERE)
- 入口:`/shipConfig/upload`。Excel 与 JSON 两路都删全表;JSON 路径不校验 ship_id 值,更危险。
- **防护建议**:导入前二次确认 + 自动备份;add_type=0 表只允许"整库覆盖"式导入。

### 【高】ShipEngineConfigServiceImpl.engineParamMenuConfigSave —— 菜单整树删
- 先 `deleteEngineMenu(shipId, menuType)` 删整棵 `tab_engine_param_menu`,再按载荷重建;健康菜单还联动同步 `mmha_component`。
- **无 @Transactional**;monitor 菜单会把不在新树的节点从 `tab_engine_param_relationship` 级联删。
- 前端某子树没展开 → 节点漏传 → 整棵菜单丢失。

### 【高】EnergyEfficiencyConfigController.setDeviceConfig —— 能效设备按载荷差量删
- 载荷里没出现的能效设备 → `deleteEquipment(shipId, uuid)` 逐个删设备+其全部 `tab_statistics_param`。
- **无 @Transactional,空载荷无防护** → 整船能效配置可被一次空提交清空。

### 【高】SpecialSignalConfigServiceImpl.save —— 按 category 删整类 device_type
- `deleteByShipIdAndDeviceType(shipId, deviceType)` 删 `tab_statistics_param`;category=all/other 覆盖几乎全部类型。
- GET 与 POST 之间数据若变化(别的页面新增了配置),本次保存会把"没在这次载荷里"的类型清掉。

### 【高】ShipNavigationConfigServiceImpl.save —— 通导整船工况点删
- `deleteNavigationParam(shipId)` = 删 `tab_engine_param where ship_id=? and order_id<=100`(整船通导点)再按载荷重插。
- 无事务;插入中途异常 → 已删的通导点不回来;船端还会重写 iscu 四表。

### 【中高】engineParamBackendConfigSave / updateDeviceRelation —— 改键级联删
- @Transactional 被注释。改 device_key 时:删旧键 stats/state 行 → 重插 → 删菜单关系重插,三段非事务。批量 `/backend/save2` 某条失败 → 参数行"删了没插回/菜单关系丢"。

### 【中】ShipEngineConfigServiceImpl.upload —— 机舱 Excel 导入(船端)
- 无事务;整船状态量清空 + 删 order_id 空工况点,逐行"删旧插新"。Excel 不全/中途错 → 状态量部分丢失。

### 【中】engineParamMoreConfigSave —— 状态量"只删不插"
- 有事务。但前端没把 stateData 原样回传(改类型/弹窗没开)时,`tab_engine_state_quantity_cfg` 该行删后不插回 → 状态量静默丢失。

### 【中】流量计/油舱保存 —— 整船删后重建
- ShipFlowmeterServiceImpl:删整船流量计/燃油密度类再插;载荷空=只删不插(有事务但载荷空不拦)。
- OilCabinConfigServiceImpl:删整船油舱菜单+舱容再插;只提交部分舱 → 其余舱被清(空载荷不删,相对安全)。

### 【中】DataCapConfigServiceImpl —— iscu 协议表非事务重建 + 级联删
- saveDataCapConfig/updateDataCapConfig/deleteOne/saveOne 的 @Transactional **全被注释**;删 hldkeymap → 重建 deviceinfo/topicinfo/channelsdataprotocol 任一环抛错 → iscu 协议表"删了没重建";被删 orderId 级联删 `tab_engine_param/statistics/state_quantity_cfg`。
- **船端采集配置页是最容易触发"配置整片消失"的地方**。

---

## 共同根因与通用防护

- **根因**:整船 `DELETE ... WHERE ship_id=?` + 重插,依赖前端每次提交"全量且完整";后端无"载荷完整性/行数"校验,多数无事务。
- **给用户的建议**:操作高风险页面(导入/能效设备/菜单/特殊信号/采集配置)前,先 `mysqldump` 或导出该船配置备份;改动尽量用 SQL 定向,别整页覆盖式保存。
- **给研发的建议**(如后续有人管):为 delete-insert 入口补 @Transactional + "期望行数≥现网行数"防护;/shipConfig/upload 加表级覆盖确认与自动备份。
