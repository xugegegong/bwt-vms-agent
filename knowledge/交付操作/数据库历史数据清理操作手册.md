# 数据库历史数据清理操作手册（tab_data_org / tab_res_clean / tab_res_status 等）

> 知识层级：**实战验证**（2026-11-27 实船执行，含分区清理约 390G、验证记录）
> 适用：船端/岸端 MySQL 5.7（iCommander 栈，库名按现场：`vms_sys_db`、`vms_<船号>_base_db`）
> 目的：解决"数据无限增长 → 磁盘/查询性能/备份时间持续恶化"，并给出**安全的删除方法**
> 前置：**任何删除都必须先和业务方确认保留期限**（报表、索赔、追溯可能依赖历史数据）

---

## 一、哪些表在涨、为什么涨

| 表 | 内容 | 增长特征（实测） | 是否有分区 |
|---|---|---|---|
| `tab_data_org`（`vms_<船号>_base_db`） | 原始采集报文（PNG hex） | **约 20G/月/船**，16 个月累计 ~300G | ✅ 按月 RANGE 分区（p202501 等） |
| `tab_res_clean`（`vms_sys_db`） | 清洗后的工况数据 | 约 6~7G/月，19 个月累计 ~100G | ✅ 按月分区（tab_res_clean_202505 等） |
| `tab_res_status`（`vms_sys_db`） | 状态流水（报警/绿色航速等始末记录） | 单表 8.4G，随状态变化频率增长 | ❌ 无分区 |
| `tab_flowmeter_record_v2` | 流量计记录 | 小~中 | ❌ 无分区 |
| `tab_res_clean_copy3` 等 `*_copy*` | 历史遗留的拷贝表 | 1~2G | 视情况 |

**先摸清现状再动手**（通用探查 SQL）：

```sql
-- 1) 各库最大的表
SELECT table_schema, table_name, table_rows,
       ROUND(data_length/1048576) AS data_mb, ROUND(index_length/1048576) AS idx_mb
FROM information_schema.tables
WHERE table_schema NOT IN ('mysql','performance_schema','information_schema','sys')
ORDER BY data_length DESC LIMIT 20;

-- 2) 分区明细（只查目标表）
SELECT TABLE_NAME, PARTITION_NAME, PARTITION_DESCRIPTION, TABLE_ROWS,
       ROUND(DATA_LENGTH/1048576) AS mb
FROM information_schema.PARTITIONS
WHERE TABLE_SCHEMA='vms_sys_db'
  AND TABLE_NAME IN ('tab_res_clean','tab_res_status')
ORDER BY TABLE_NAME, PARTITION_ORDINAL_POSITION;
```

## 二、分区表的清理（tab_data_org / tab_res_clean）——用 TRUNCATE PARTITION

### 2.1 为什么用 TRUNCATE PARTITION 而不是 DELETE / DROP PARTITION

| 方法 | 速度 | 磁盘释放 | 对业务影响 | 备注 |
|---|---|---|---|---|
| `DELETE ... WHERE` | **极慢**（几十G表要几小时） | 慢（碎片不释放） | 长事务、大量binlog | ❌ 不用 |
| `DROP PARTITION` | 秒级 | 立即 | 分区**定义消失**，历史补齐任务往该月插入会报错"no partition for value" | ❌ 慎用 |
| **`TRUNCATE PARTITION`** | 秒级~分钟级 | 立即 | 分区**定义保留**（插入仍可用，只是数据空） | ✅ **推荐** |

### 2.2 确认分区口径

- 分区名 = **该月包含的数据**（`tab_res_clean_202609` 装的是 2026 年 9 月数据）；
- `PARTITION_DESCRIPTION` = **下月 1 日的 UTC 秒值**（用于核对，不用于改写）；
- 删除粒度是**整月**：如"保留 3 个月"实际是"保留最近 3 个完整月"，边界月会多留/少留几天，属正常。

### 2.3 操作步骤

**第 1 步：备份（二选一）**

```sql
-- 方案A:整表结构+数据导出(大表慎用,时间久)
-- 方案B(推荐):只备份将被删的分区为归档表(数据量大时也建议走 mysqldump 到文件)
-- 最简单:确认业务方知晓并同意删除,至少把"将删哪些分区"记录在案
```

> 实船经验：`tab_data_org` 每月 20G，整表 dump 不现实。**删除前必须业务确认**；如需留档，按分区导出（`SELECT * FROM tab PARTITION (p202508) INTO OUTFILE ...`）或做文件级备份。

**第 2 步：先停长查询（防 MDL 锁堵死）**

```sql
-- 查 >120 秒的长查询;有就先评估(报表类可 KILL)
SELECT ID, TIME, STATE, LEFT(INFO,60) FROM information_schema.PROCESSLIST
WHERE COMMAND='Query' AND TIME>120 AND INFO NOT LIKE '%TRUNCATE%';
-- 如确认可杀:
KILL <ID>;
```
**教训**：`TRUNCATE PARTITION` 需要排他 MDL 锁。曾有报表查询跑了 66 分钟占着锁，导致 TRUNCATE 排队 20 分钟且把该表所有 INSERT（实时入库）一起堵死。**执行前必须确认没有长查询。**

**第 3 步：执行清理**（按保留期限列出要删的分区）

```sql
-- 例:保留最近 3 个月(2026-09/10/11),清掉 2026-08 及以前
ALTER TABLE vms_30005008_base_db.tab_data_org
  TRUNCATE PARTITION p202509,p202510,p202511,p202512,
                     p202601,p202602,p202603,p202604,
                     p202605,p202606,p202607,p202608;

ALTER TABLE vms_sys_db.tab_res_clean
  TRUNCATE PARTITION tab_res_clean_202505,tab_res_clean_202506,tab_res_clean_202507,
                     tab_res_clean_202508,tab_res_clean_202509,tab_res_clean_202510,
                     tab_res_clean_202511,tab_res_clean_202512,tab_res_clean_202601,
                     tab_res_clean_202602,tab_res_clean_202603,tab_res_clean_202604,
                     tab_res_clean_202605,tab_res_clean_202606,tab_res_clean_202607,
                     tab_res_clean_202608;
```
> 分区列表务必先用上面的"分区明细"SQL 导出核对，不要凭记忆写。

**第 4 步：确认进度**（大表 TRUNCATE 可能数分钟到数十分钟）

```sql
-- 每5分钟看一次:目标分区 TABLE_ROWS 归 0 即删完
SELECT PARTITION_NAME, TABLE_ROWS FROM information_schema.PARTITIONS
WHERE TABLE_SCHEMA='vms_sys_db' AND TABLE_NAME='tab_res_clean'
  AND PARTITION_NAME BETWEEN 'tab_res_clean_202505' AND 'tab_res_clean_202608'
  AND TABLE_ROWS>0;
```

**第 5 步：验证**

```bash
df -h                                  # 磁盘释放(实船:19%→8%)
docker stats --no-stream --format '{{.Name}} {{.CPUPerc}}' | grep mysql
```

## 三、非分区表的清理（tab_res_status 等）——分批 DELETE

`tab_res_status`（8.4G）无分区，不能 TRUNCATE PARTITION。推荐**分批删除**，避免大事务锁表：

```sql
-- 循环执行,直到影响行数为 0(每批 5000 行,一批约几秒)
DELETE FROM vms_sys_db.tab_res_status
WHERE ship_id = <船号>
  AND start_utc < UNIX_TIMESTAMP(DATE_SUB(NOW(), INTERVAL 90 DAY))
LIMIT 5000;
```

**要点**：
- **一定要带 `ship_id` 和 `start_utc` 条件**，别全表 DELETE；
- **一定要 `LIMIT`**，否则 8.4G 表可能锁死；
- 删除后检查碎片：`OPTIMIZE TABLE`（会锁表，选低峰）或后续按需重建；
- **更好的长期方案**：让研发把这表也改成分区表（按月），后续就能用 TRUNCATE PARTITION。

```sql
-- 先看一眼表的年龄和行数(决定删到哪)
SELECT COUNT(*) AS 总行数, FROM_UNIXTIME(MIN(start_utc)) AS 最早, FROM_UNIXTIME(MAX(start_utc)) AS 最新
FROM vms_sys_db.tab_res_status WHERE ship_id=<船号>;
```

## 四、顺带的索引与碎片整理（可选，需低峰）

大表删除后索引统计会失真，建议：

```sql
ANALYZE TABLE vms_sys_db.tab_res_clean;     -- 刷新统计,让优化器重新选择执行计划
```

> `OPTIMIZE TABLE` 对 InnoDB 会重建表（锁写），大表耗时长，仅在确需回收碎片空间时做。

## 六、踩坑记录（务必看）

1. **DDL 被 MDL 锁堵住**：`TRUNCATE PARTITION` 显示 `Waiting for table metadata lock` 时，不是"卡死"，是被长查询占着。用 `information_schema.PROCESSLIST` 找 `TIME` 大且 `INFO LIKE '%表名%'` 的 SELECT，`KILL` 后立即继续。期间该表所有 INSERT 也会被堵（实时入库会暂停），属正常连带，别误判为写入故障。
2. **查 DDL 是否还在跑**：`WHERE INFO LIKE '%ALTER TABLE%'` 会**匹配到查询自己**，应改 `WHERE COMMAND='Query' AND INFO LIKE 'ALTER%'`；索引是否建成用 `SHOW INDEX` 确认。
3. **别用 `DELETE` 清分区表**：慢且产生海量 binlog，用 `TRUNCATE PARTITION`。
4. **别用 `DROP PARTITION`**：分区定义没了，历史数据补齐（`VMSHistoryRebuild`/`pykafka` 补数任务）往老日期插入会直接报错。TRUNCATE 保留定义，安全。
5. **注意服务器时区**：船端服务器是 UTC，日志时间 02:xx = 北京 10:xx，别把时间戳搞混导致算错保留期。
6. **`tab_res_clean_copy3` 等遗留拷贝表**：确认无人使用后可 `DROP TABLE`（这是真删表，需业务确认）。
7. **操作窗口**：选业务低峰，避开每 5/10 分钟的定时任务密集时段（减少锁竞争）。

## 七、推荐的定期维护策略

1. **按月执行**：每月初清理"保留 N 个月"以外的分区（N 由业务定，常见 3~6 个月）；
2. **可做成 cron 脚本**（需业务确认保留期后固化）：

```bash
#!/bin/bash
# 每月1日清理 6 个月前的分区(示例,按实际库/表/分区名调整)
MYSQL="docker exec mysql mysql -uroot -p<密码>"
KEEP_MONTHS=6
# 生成要删的分区列表逻辑(同第二章查询),再拼接 ALTER ... TRUNCATE PARTITION
```

3. **监控项**：磁盘使用率 >70% 告警、`information_schema.tables` 月增量趋势、慢查询 TOP 10。
4. **优先级**：`tab_data_org`（20G/月，最大）> `tab_res_clean`（6G/月）> `tab_res_status`（按状态频率）。
