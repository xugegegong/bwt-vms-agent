# 缺陷单：system 服务航速优化定时任务每 10 分钟打爆堆内存，导致生产中断

> 日期：2026-11-27
> 严重级别：**P0（生产中断，已多次造成全船服务不可用）**
> 影响服务：`bwt-vms-system`
> 代码位置：`com.bwt.vms.system.service.energy.impl.SpeedOptimizeSeriveImpl` + `com.bwt.vms.system.entity.vo.energy.SpeedPlanningNaryTree`

## 一、现象（现场多次复现）

现象因服务叠加而表现为多种形式，容易误判为不同故障：

1. system 服务正常运行约 10~30 分钟后，Web 页面登录失败（8085 端口 Tomcat 无响应）；
2. system 日志持续刷 Kafka 重平衡日志（实测每分钟 10~12 条）：`Group coordinator ... is unavailable or invalid ... will attempt rediscovery`、`Commit cannot be completed since the group has already rebalanced ... max.poll.interval.ms`；
3. nacos 服务列表中 `bwt-vms-system` 实例消失或健康状态抖动；
4. system 容器 CPU 打到 100%（单核），`jstat` 显示老年代 100%、Full GC 次数暴涨（实测 11330 次 / 累计 58701 秒）；
5. JVM 卡死在 Full GC 中，`jcmd/jmap` 无法 attach（`AttachNotSupportedException`）；
6. 只能重启 system 临时恢复，1~2 小时后再次复发。

## 二、根因（已实测锁定）

### 2.1 直接原因

`SpeedOptimizeSeriveImpl` 中有一个定时任务：

```java
@Scheduled(cron = "0 1/10 * * * ?")   // 每 10 分钟执行一次
public void speedOptimialTask() { ... }
```

该任务对**数据库中所有船**逐条执行 `speedOptimial(shipId)`，其核心是 `optimal()` → `SpeedPlanningNaryTree.buildTree()`。

`buildTree` 是**全枚举组合树**实现：

```java
// SpeedPlanningNaryTree.java:25-104
for (Double rpmValue : rpmRange) {                      // 每一层枚举所有转速档位
    List<Double> rpmSeries = new ArrayList<>(parentNode.rpmSequence);   // 每节点拷贝完整序列
    rpmSeries.add(rpmValue);
    List<Double> speedSeries = new ArrayList<>(parentNode.speedSequence); // 再拷贝一份
    speedSeries.add(speed);
    ...
    buildTree(currentNode, leftRouteNum - 1, ...);      // 递归下一段
}
```

节点总数 = **转速档位数 ^ 航段数**（指数级），且每个节点额外持有两个 `ArrayList` 的全量拷贝（内存再乘一个"深度"系数）。

### 2.2 实测数据（2026-11-27，船 30005008）

| 指标 | 数值 |
|---|---|
| 采样 21 分钟内 `SpeedPlanningNaryTree$TreeNode` 增量 | **+798,406 个**（从 475 万涨到 555 万） |
| 同步增长的 `java.lang.Long` / `java.lang.Double` / `ArrayList` | 各 +79.8 万个（1:1:1 对应，即每个节点产生一个 Long + 一个 Double + 列表） |
| 堆使用 | 2048m 堆在任务执行后 10~30 分钟内被填满 |
| Full GC | 单次平均约 5 秒，累计 58701 秒（16.3 小时） |

### 2.3 触发条件（三者同时满足才会爆）

1. 该船在 `tab_ship_info_extend` 中配置了转速规划参数：`Planning_rpm_min`、`Planning_rpm_max`、`RPM_planning_step`；
2. 该船 `tab_flight_record` 最新航次的 `estimated_end_time`（预计到达时间）是未来时间（正在航行）；
3. 航程中的航段数量较多（`combineSegment` 后 `decisionMakingSegmentNum` 较大）。

## 三、复现与验证方法

```
1. 检查参数：SELECT ... FROM tab_ship_info_extend JOIN tab_ship_param_model ... WHERE param_name_en IN ('Planning_rpm_min','Planning_rpm_max','RPM_planning_step')
2. 检查航次：SELECT estimated_end_time FROM tab_flight_record WHERE ship_id = <id> ORDER BY flight_start_time DESC LIMIT 1
3. 观察任务日志：
   docker logs system | grep -E '航速优化功能定时任务运行|规划航段数量|转速规划列表'
   —— 出现"规划航段数量：N"即开始建树；N 越大风险越高
4. 观察堆：
   docker exec system sh -c 'jstat -gcutil $(pgrep java) 5000'
   —— 任务点(每10分钟第1分钟)之后 O 列出现尖峰即为复现
5. 抓堆直方图（在 O>40% 时，jmap -histo，不要用 jcmd 会触发 FullGC）：
   docker exec system sh -c 'J=$(pgrep java); JP=$(readlink -f /proc/$J/exe); $(dirname $JP)/jmap -histo $J | head -30'
   —— 排名前列出现 SpeedPlanningNaryTree$TreeNode 即坐实
```

## 四、建议修复方案（二选一或组合）

### 方案 A：分支限界剪枝（推荐，治本）

在 `buildTree` 递归时，实时计算当前已耗时 `costTime`，若 `etd + costTime > eta` 直接 `return`，不再展开该子树。对于 ETA 约束强的场景，剪枝率可达 90% 以上。

### 方案 B：避免每节点全序列拷贝

`rpmSequence` / `speedSequence` 改为只在**叶子节点**物化（或用链表 + 父指针回溯），中间节点只存当前选择值。内存占用从 O(节点数×深度) 降到 O(节点数)。

### 方案 C（短期运维规避，非代码修复）

运维侧已通过删除该船的 `Planning_rpm_min`/`Planning_rpm_max`/`RPM_planning_step` 三个配置参数，使 `generateRpmPlanningList` 返回空列表，任务在**建树之前**即返回（实测任务耗时 23ms，TreeNode 归零、FGC=0）。

**操作四步（现场已验证）**：

1. **查**（确认参数存在 + 最新航次 ETA 在未来）：
```sql
SELECT i.id, i.ship_id, m.param_name, m.param_name_en, i.param_value
FROM vms_sys_db.tab_ship_info_extend i
LEFT JOIN vms_sys_db.tab_ship_param_model m ON i.param_id = m.id
WHERE i.ship_id = <船号>
  AND (m.param_name_en IN ('Planning_rpm_min','Planning_rpm_max','RPM_planning_step')
       OR m.param_name IN ('航速优化最小规划转速','航速优化最大规划转速','航速优化转速规划粒度'));

SELECT id, flight_number, FROM_UNIXTIME(estimated_end_time) AS eta
FROM vms_sys_db.tab_flight_record WHERE ship_id=<船号> ORDER BY flight_start_time DESC LIMIT 3;
```
2. **备**：
```sql
CREATE TABLE IF NOT EXISTS tab_ship_info_extend_bak_YYYYMMDD AS
SELECT * FROM vms_sys_db.tab_ship_info_extend WHERE ship_id=<船号>;
```
3. **删**：
```sql
DELETE i FROM vms_sys_db.tab_ship_info_extend i
LEFT JOIN vms_sys_db.tab_ship_param_model m ON i.param_id = m.id
WHERE i.ship_id = <船号>
  AND (m.param_name_en IN ('Planning_rpm_min','Planning_rpm_max','RPM_planning_step')
       OR m.param_name IN ('航速优化最小规划转速','航速优化最大规划转速','航速优化转速规划粒度'));
```
无需重启，下个整十分钟点生效。
4. **验**：等 12 分钟后查日志，应出现 `规划转速列表为空，航速优化功能无法计算` 与 `航速优化功能定时任务运行结束`（毫秒级），不出现 `规划航段数量`；`jmap -histo` 中 `SpeedPlanningNaryTree$TreeNode` 归零。

**备选/应急（临时）**：清最新航次 ETA 同样能在建树前 return——`UPDATE tab_flight_record SET estimated_end_time=NULL WHERE ship_id=<船号> ORDER BY flight_start_time DESC LIMIT 1;`（先备份）。缺点是**船员下次填航次即复发**，且页面"预计到达时间"显示为空，只作应急；稳定开关是转速参数。

**注意**：方案 C 只对"删除参数的船"有效；其他船只要配了参数且有未来 ETA 就会复发。因此**必须做代码修复**。

## 五、影响面

- 该缺陷从代码上看是**所有船通用**的，不是单船问题；
- 只要某船：配了转速参数 + 有航行中航次 + 航段数较多，就会周期性打爆堆；
- 严重度随航段数指数上升，舰船长途航线（多航段）比短途更容易触发；
- 目前已知船 30005008 触发，建议排查所有已交付船舶是否配了上述三个参数。

## 七、次要问题（同一次排查发现，建议一并优化）

`TrimOptimizeServiceImpl.reloadTrimConfig()`（`@Scheduled(cron = "0 0/10 * * * *")`）每 10 分钟对 `tab_trim_relation` / `tab_hydrostatic_trimmed` 执行 `selectAll()` 全表加载，覆盖写入内存 Map（旧对象变垃圾）。实测每轮产生约 9 千个对象垃圾 + 一次全表查询。**不导致本次故障**（强制 Full GC 后老年代 90%→37%，仅耗时 1 秒，垃圾可回收），但属于周期性浪费（DB 全表扫描 + 内存抖动），建议改为按船/按变更 reload 或增大间隔。

**判定"泄漏 vs 垃圾堆积"的方法（本次实测验证）**：
```
jcmd <pid> GC.run && jstat -gcutil <pid>
→ O 90%→37%（回落）= 垃圾,JVM 正常锯齿,无需处理
→ O 100%→100%（不回落）= 活对象撑满,真泄漏（本次建树缺陷即此类）
```
