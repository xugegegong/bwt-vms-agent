## 1. 背景与目标

**现状**:系统在役、数据持续流转、前任研发离职无资料。已梳理出 30 条诊断(P0×8 / P1×11 / P2×11),核心硬伤集中在:鉴权不严、工况数据可能丢、新老链路并存互相覆盖、报表无预聚合、前端实时数据流混乱、技术栈老旧。

**重构目标**(按优先级):
1. **止损**:消除安全漏洞与数据丢失风险(P0,最高)
2. **收敛**:消除新老并存,降低理解与维护成本(P1 架构)
3. **提速**:解决报表/导出性能瓶颈(P1 性能)
4. **还债**:实体统一、拼写、工具链、测试(P2)
5. **可持续**:建立可观测、配置校验、CI/CD 长效机制

**成功标准**:P0 清零;新老链路合并为单一主线;报表 P95 响应 < 3s;核心算法有单测兜底;20 份文档持续对齐代码。

---

## 2. 重构策略与原则

1. **绞杀者模式(Strangler Fig)**:新逻辑走新模块新契约,与旧实现双写/双查并行期对比,验证后切量下旧。绝不大爆炸重写。
2. **价值驱动排序**:P0 止损 → P2 架构 → P3 性能 → P4 技术债。不追求完美架构,优先"能跑+安全+可维护"。
3. **灰度优先**:每个改动都过灰度(影子模式 → 小比例 → 全量),配 feature flag 可秒级回退。
4. **测试先行**:核心算法(SFOC/CII/EEXI/DBSCAN/Douglas-Peucker)先补单测,再动;关键链路补契约测试。
5. **专项小组多线并行**:后端安全组、后端架构组、前端组、DBA/运维组、测试组并行推进,靠契约解耦。
6. **配置治理前置**:改代码前先建配置完整性校验,避免改了才发现静默依赖。
7. **可度量**:每个阶段有量化验收(监控指标对比基线)。

## 10. 灰度发布通用策略

**专项小组 + 可灰度**的核心风险控制。四种灰度模式:

1. **影子模式(Shadow)**:新逻辑运行但不生效,只记录"如果生效会怎样",对比旧逻辑差异。用于鉴权、能效计算等高风险改动。
2. **按船灰度**:选 1-2 艘试点船切新链路,观察 N 天,逐步扩量。用于数据链路、船岸同步。
3. **按比例/按路由灰度**:网关层按流量比例或路由切量。用于 FastJSON、网关鉴权。
4. **按页面灰度(前端)**:新页面用新通道,老页面逐步迁。用于实时通道统一、巨石拆分。

**通用要素**:
- **Feature Flag**:每个改动有开关,可秒级回退(Nacos 配置中心下发)
- **双写/双查期**:新老并行,数据一致性校验脚本(差异超阈值报警)
- **降级预案**:每改动有"降级回旧"的明确步骤与演练
- **观察窗**:小比例至少观察 3-7 天再扩量

## 11. 关键技术决策详解

### 11.1 绞杀者模式落地(实时数据收敛)
新建独立"能效/工况计算服务"(或强化 dataCleanV2),与 realTimeData **双写 Redis** 并行;部署一致性校验 Job 每日对比 `energy:*`、`list:ship:*:other` 差异;差异 < 阈值后,前端查询切新服务;切量完成 1-2 周观察稳定后下线 realTimeData 重复计算。全程可 flag 回退。

### 11.2 数据库不换
MySQL/PG 保持。收益:换库风险极高且收益不抵。改做:分区自动化、索引审计、慢查询治理、连接池统一。PG WAL 保留期调大 + 监控告警。

### 11.3 实时通道统一(前端)
废弃 `window.warn` 全局变量 + `setInterval` 拉取 + 多页面 `window.WS.onmessage` 重复挂载(当前 D03/D04/D09 多处互覆盖)。改为:单一 WS 连接管理器 → 消息分发到 MobX store/Context → 组件 `@observer` 响应式更新。好处:数据流可追踪、无重复订阅、易测试。

### 11.4 配置驱动治理
建"配置完整性校验服务":按船扫描 tab_engine_param/tab_statistics_param/tab_tank_device/tab_height_cabin/tab_ship_info_extend/mmha_component/tab_alarm_mapping,输出"配置健康度报告"(配了什么、缺什么、影响哪个功能)。前端配置中心集成。根治"配错静默算不出"。

### 11.5 system 巨石
450+ 接口的 system 先按业务域分包(D01~D16 目录)治理;微服务再拆分(如拆出 auth/energy/oilwater 独立服务)优先级低,放 P4 评估,取决于团队规模与性能瓶颈。

## 12. 风险矩阵与回退预案

| 风险 | 概率 | 影响 | 对策 |
|---|---|---|---|
| 业务需求插入打乱节奏 | 高 | 中 | 预留 20% 容量;需求按 P0-P2 排序并入 |
| 重构引入数据错误 | 中 | 高 | 双写对比脚本 + 算法单测 + 灰度;错误超阈值自动报警/回退 |
| 双链路收敛期数据不一致 | 中 | 高 | 一致性校验 Job;差异阈值;可切回旧链路 |
| 前端巨石拆分回归 | 中 | 中 | 充分回归 + 按页面灰度;保留旧组件可回退 |
| 前端工具链升级失败 | 中 | 高 | 单独立项评估;先建 Vite 试验田;失败则保留 Webpack3 |
| 老代码理解偏差 | 中 | 中 | 20 份文档兜底;改动前复核代码;Code Review |
| Kafka 消费组重置(groupId 改名) | 低 | 中 | 双消费组并行期;监控 lag |
| 灰度期资源不足 | 中 | 中 | 专项小组保障;灰度基础设施先行(P0) |

**回退总原则**:所有改动 feature flag 化,任何改动 30 分钟内可回退到上线前状态。

## 13. 度量与验收

**P0 基线(准备期采集)**:接口 P95 RT、错误率、Kafka lag、Redis 命中率、报表响应、工况数据完整性、报警数。

**阶段验收量化**:
- P1:鉴权扫描通过;死信队列监控为空;WS 重连成功率 > 99%
- P2:`energy:*` 一致性差异 < 0.1%;db2 退役;AIS 死代码 0;前端实时通道单一
- P3:能效报表 P95 < 3s;导出 HTTP 线程不阻塞;tab_behavior_recognition 体积降 > 80%
- P4:核心测试覆盖 > 60%;实体单一;前端巨石拆分(单文件 < 800 行)

**每阶段产出**:阶段总结报告(改动清单、验收数据、遗留问题、下阶段调整)。

## 14. 不做的事(防范围蔓延)

- **不换语言/框架底座**:Spring Cloud 保留,只升版本(Spring Boot 2.1→2.7 是上限,不建议跨大版本)
- **不一次性重写前端**:React 保留,antd/Webpack 渐进升级或单独立项
- **不换数据库**:MySQL/PG 保持
- **不追求微服务全面拆分**:system 内部治理优先,服务拆分按需
- **不引入新中间件除非必要**:Kafka/Redis/Nacos 够用,不引入新 MQ/缓存除非有强需求
- **不在重构期做新业务功能**:业务需求走正常迭代,不混入重构分支
